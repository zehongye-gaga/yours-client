# 微内核职责与产品需求映射

记录日期：2026-10-24。Cordis core 已作为可维护的本地分支引入；产品服务与运行环境仍待实现。

微内核解决运行时能力的组合与生命周期问题：让插件找到需要的服务，在依赖满足时启动，在依赖变化时协调停止或重新激活，并在退出时回收已登记的资源。它为插件化产品提供共同的运行规则。

本文分别说明 Cordis core 提供的机制，以及 Yours Client 基于这些机制需要承担的产品需求。具体接口见[微内核设计](microkernel-design.md)，尚需确定的行为见[设计问题](cordis-design-questions.md)。

## Cordis 内核解决的问题

### 插件如何发现和使用彼此的能力

插件通过 Context 获取服务，通过服务标识依赖能力。服务提供者可以独立实现和挂载，消费者通过约定的接口使用它。Context 的派生与隔离机制为不同上下文提供不同服务绑定。[Context 实现](https://github.com/cordiverse/cordis/blob/35fdc969e4b6c48c48ed44717c7a018324e4dd88/packages/core/src/context.ts)、[服务注册实现](https://github.com/cordiverse/cordis/blob/35fdc969e4b6c48c48ed44717c7a018324e4dd88/packages/core/src/reflect.ts)

### 插件什么时候可以运行

插件声明服务依赖，运行实例根据依赖的可用性决定是否激活。服务提供者变化会触发相关实例重新计算运行状态，插件组合可以随运行环境变化。[依赖注入入口](https://github.com/cordiverse/cordis/blob/35fdc969e4b6c48c48ed44717c7a018324e4dd88/packages/core/src/registry.ts)、[实例状态协调](https://github.com/cordiverse/cordis/blob/35fdc969e4b6c48c48ed44717c7a018324e4dd88/packages/core/src/fiber.ts#L395)

### 停止插件时如何释放其影响

服务注册、事件监听和其他登记到 effect 的资源与插件生命周期关联。卸载时执行清理；提供者释放资源前等待依赖消费者完成卸载，使消费者有机会使用依赖完成收尾。插件需为自行创建的连接、定时器等资源登记清理逻辑。[effect 与卸载实现](https://github.com/cordiverse/cordis/blob/35fdc969e4b6c48c48ed44717c7a018324e4dd88/packages/core/src/fiber.ts)

### 插件如何通过事件协作

事件服务提供通知和不同分发模式，使插件能在约定的事件点观察或参与流程。分发顺序、是否等待和错误传播取决于具体模式；使用事件时需要明确这些契约。[事件实现](https://github.com/cordiverse/cordis/blob/35fdc969e4b6c48c48ed44717c7a018324e4dd88/packages/core/src/events.ts)

这些是进程内的框架机制。产品里的 Workspace、Agent 工具、Mini App、权限和跨进程协议需要在框架之上定义。

## 对应 Yours Client 的产品需求

下表的“内核”专指当前引入的 Cordis。产品身份、Workspace 和业务注册事务由外层服务负责。

| 产品需求 | 微内核承担的职责 | 配合完成需求的其他层 |
| --- | --- | --- |
| 启用一个插件后可以使用其能力 | 建立 Fiber，解析服务依赖，运行插件并管理服务注册 | 安装服务验证和准备代码；运行适配器加载入口 |
| 随时停止或卸载一个插件 | 协调受影响 Fiber、撤销受管注册并调用清理；任务取消需协作 | Supervisor 停止进程；安装服务处理代码文件与数据保留 |
| 更换模型或其他能力实现 | 通过服务契约连接消费者和提供者，协调服务替换引发的依赖变化 | 模型适配器负责模型协议、请求、流式结果和凭证使用 |
| 不同 Workspace 有不同能力组合 | 提供 Context 派生与按服务键 isolate；产品范围由宿主映射 | Workspace 管理分配 realm 或独立 Context；Profile 和 Policy 决定启用及授权 |
| 插件启动后出现工具和界面 | 提供 effect 和插件生命周期，用于绑定业务清理 | Tools / Views 管理业务注册和修订；Renderer 与 Bridge 展示和操作界面 |
| 业务插件可以升级 | 管理新旧 Fiber 和受管资源；内部 epoch 不作为远程身份 | 注册服务提交批次与修订；部署服务预热；Broker 固定快照；Runtime 排空 |
| 插件失败后能解释原因并清理 | 提供 Fiber 状态、失败与清理信息；产品诊断另行汇总 | Supervisor 检测进程退出；管理界面显示诊断；重试策略决定是否再次启动 |
| 客户端重启后恢复工作环境 | 提供可重建的实例与生命周期入口，按依赖重新激活 | 宿主保存启用配置与版本；存储服务保存会话和业务数据，并处理未完成操作 |

Cordis 对已指定的服务键提供隔离；Workspace 范围必须由宿主明确映射。进程崩溃隔离、文件访问隔离和用户授权需要运行环境与权限服务提供。

## 各层负责的完整功能

| 需求或功能 | 主责层 | 微内核与该层的关系 |
| --- | --- | --- |
| 思考、选择工具、执行 Agent Step | Agent Runtime | 为其提供依赖、生命周期和可用服务 |
| 调用模型和处理模型流式协议 | Model Provider | 管理适配器服务，具体请求由适配器执行 |
| MCP 协议与工具输入输出校验 | MCP Adapter 和 Tool Registry | 管理服务与注册项，不理解具体工具业务 |
| 下载、校验、安装和分发插件包 | Installer 和 Package Store | 接收已准备好的插件定义或运行描述 |
| 创建、监控和终止 Node 子进程 | Process Supervisor | 接收启动结果与故障事件，协调逻辑实例状态 |
| 系统沙箱、网络和文件访问限制 | Host Sandbox 和 Capability Broker | 传递绑定的实例身份，权限判定与隔离由对应层执行 |
| 页面渲染、布局、UI 数据同步 | View Host 和 UI Bridge | 管理界面注册的有效性，提供运行事件 |
| 数据持久化、备份和迁移 | Storage 和部署服务 | 管理服务生命周期，不把清理函数当作数据回滚事务 |
| 配置叠加和个性化工作台 | Profile Resolver | 按解析结果建立作用域并启用插件实例 |

例如“插件热升级”包含代码准备、就绪检查、注册切换、旧调用处理、资源释放和数据兼容，需由多个层共同完成。Cordis 直接负责进程内 Fiber 与受管资源，跨 Tools / Views 的一致性由产品注册服务实现。

## 需要在 Cordis 机制之外补充的设计

- **产品身份和作用域**：明确包、实例、激活代次与 Root、Workspace、Session 的关系。
- **跨进程契约**：定义 RPC、序列化、绑定身份、权限校验、超时、取消与断线处理。
- **注册批次和修订**：使工具、UI 等业务注册项以一致版本提交，避免部分发布。
- **调用版本一致性**：让一个 Agent Step 的工具定义和执行目标保持一致，支持旧调用排空。
- **产品恢复策略**：定义重启恢复、版本回退、数据兼容和失败诊断。

上述内容是 Yours Client 的设计目标，不能因直接复用 Cordis 就视为已经具备。原生事件和清理语义按本地 Cordis 源码执行；需要更改时记录分支变更并补充测试。

## GitHub 工作台中的职责示例

| 用户或系统事件 | 微内核的工作 | 业务与宿主的工作 |
| --- | --- | --- |
| 用户启用 GitHub 插件 | 创建实例，检查服务依赖并安排激活 | 安装服务准备包，运行适配器启动 Node 后端 |
| 插件准备完成 | 完成原生服务初始化；业务暂存与提交由注册服务执行 | 注册服务发布完整工具和 UI 修订；界面显示面板，插件读取数据 |
| 用户让 Agent 查询项目 | 提供有效的服务与注册状态 | Agent 选择工具，Broker 路由调用，插件请求 GitHub |
| 插件获得新数据 | 维持事件订阅的归属与有效性 | 插件保存数据，UI 通道传递变化，Renderer 更新页面 |
| 用户停止插件 | 停用实例并撤销注册，执行清理 | 插件关闭连接和定时任务，Supervisor 结束进程 |
| 用户安装新版本 | 管理新旧 Fiber 与资源 | 注册服务切换修订；部署检查候选，调用方保留旧快照，Runtime 排空 |

## 内核阶段的验收需求

原生测试和项目样例已接入；下面同时列出需要继续在产品层验证的行为：

1. 消费者先挂载时等待依赖；提供者出现后自动激活。
2. 对指定服务键使用独立 realm，可以解析到不同实现；完整 Workspace 策略继续实现。
3. 提供者停止时消费者先完成清理；服务恢复后消费者可以重新激活。
4. 插件激活中被取消，后续产生的资源被清理，旧激活不能发布新能力。
5. 产品注册服务的一项准备失败时，整个批次不可见；成功时读者获得完整修订（待实现）。
6. 对需要全部完成的清理定义独立 effect 或错误汇总，验证幂等、失败和消费者释放次序。

这些验收分别支撑插件组合、按场景配置、可靠启停、异步取消、完整发布和故障定位。Node 进程、真实模型、UI 与持久化的完整产品验收继续由对应层完成。
